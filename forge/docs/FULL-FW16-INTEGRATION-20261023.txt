一、现有实现与来源，哪些保留、哪些不能当最终接入

1. Forge 训练/导出/按队配置/队列/比赛/证据索引骨架可保留。
   docs/PROGRESS.md 将初版集成归于 Opus；本地无这两天的 Git 提交，不能逐行可靠断言作者。
   后续复核应按源码快照、实际产品哈希和运行时间戳归属，不按聊天中的口头完成声明归属。

2. BoosterDeployWalkingEngine 与 1.6 forward/side/turn 权重的局部适配可保留作对照。
   它依赖 B-Human MotionEngine、起身、踢球与相位处理，不满足完整原厂运动链目标。
   三个 actor 属可选全身 AMP 行走，不能代表原厂 Humanlike、其他模式、恢复、踢传控制器。

3. sim/vk1.py 是公开接口的行为建模和三 actor 孪生体。
   它有明确列出的假设，并非原始固件控制器。现有 bridge 的通过结论不能迁移成完整 1.6 资格。
   可继续作独立 sim2sim 对照；原始控制器闭环应是另一个显式后端。

4. 本机 third_party/booster-deploy-7bb1462e2ac7 是公开部署代码，README 要求固件 >=1.7.2。
   不能把它当作完整 1.6 控制器源码。SDK 提供请求/消息接口，也不等同于原厂内部运动实现。

5. 真实 1.6.0.10 原包保留了 ARM mck、动态库、配置与模型。
   当前没有一份可直接编译成等价 PC 完整 1.6 控制器的源码树。
   可以原样运行 ARM 控制核心并替换 IO 边界，避免逐模式重写和混入 B-Human 动作。
   Webots 0.0.1 PC runner 是较旧 TCN 栈，缺少本包新模块，不能作为完整 1.6 替代。

二、当前运控中间实现

B-Human 渲染相机 / 感知 / 足球高层
        |
        v
统一原厂运动请求与状态适配（模式、m/s 速度、头臂、起身、踢传、视觉输入）
        |
        +-- SimRobot 后端：每个候选机器人一个隔离的原始 ARM mck / 模块图
        |      QEMU + 原厂 RPC + 原始 500 Hz 控制器与真实原厂仿真时钟
        |      串联状态 -> 原厂踝 IK/Jacobian -> 原始并联控制图
        |      原始 MIT 命令 -> 电机域饱和 -> J^T 力矩 -> 串联 FullActuator
        |      SimRobot 真实关节/IMU/接触状态返回下一物理周期
        |
        +-- 真机后端：Booster SDK / DDS 与原厂 Loco RPC -> 同一 1.6 原生控制器
               仿真 interposer 和虚拟身份不进入真机硬件 IO 通路

这条路线复用原厂模式、命令整形、状态估计、行走、保护、起身、踢传与动作叠加逻辑。
QEMU 只解决架构执行；不把墙钟 500 Hz 或实时性能当作默认保证。
仿真必须按物理 2 ms 锁步，允许整场比真实时间慢；原厂内部定时仍由原始 GetTime 驱动。

四、下一步必须实现的 SimRobot 完整 provider

1. 在独立变体新增 BoosterNativeMotionProvider，整体替换候选机器人的低层运动输出。
   接管 JointRequest、MotionInfo、OdometryData、ArmMotionInfo、HeadMotionInfo 的有效来源。
   不让 WalkingEngine、GetUpEngine、踢球相位继续代管候选动作；官方队仍选官方 provider。
   不能只给 WalkingEngine 新建一个子类后仍声称全量接入。

2. 每个候选机器人有独立原厂进程、socket、模式、历史、输出序号和证据目录。
   不共享原厂全局变量或模式管理器，防止 3v3 中机器人之间相互污染。
   慢启动在仿真作业准备阶段完成；超时、取消和退出只结束本作业自己的进程树。

3. 用 JointSensorData 的 physicsTick / physicsTime / physicsStepLength 绑定 IO。
   同一物理 tick 再次调用 Motion 模块只复用同一份回复，不能推进第二个原厂 2 ms 周期。
   若跳过了物理 tick，拒绝继续资格评测；不能用重复旧传感器补帧掩盖时序缺口。
   FrameInfo/Motion 审计也使用同源物理时间，修复现有 60 physics / 61 Motion 采样的问题。

4. 明确速度/步行目标的转换：直接速度用 m/s、rad/s；目标位姿使用同一导航适配器。
   为球位置、头部目标、踢/传请求等建立来源与坐标系契约，接入原厂对应输入。
   原厂 VisualKick 的视觉依赖必须实测；仅调用 start/version RPC 不等于复现视觉踢球。
   不能偷偷使用球场真值替代 B-Human 的正常相机感知。

5. 当前审计白名单只覆盖部分原厂 RPC，Custom=3 及完整 LowCmd 输入等仍需补齐和核对。
   先按本机 SDK、原厂枚举/配置及实际响应建立所有 K1 模式/动作表，再开放对应本地接口。
   对不支持或被原厂拒绝的动作明确返回结果，不用 B-Human 动作静默兜底。

6. 停止、超时、NaN、掉线和未来/过期帧采用明确的失败状态。
   停止时使用已验证的 STOP/ACK 边界，保留原始最后一帧，不执行厂商服务/安装脚本。

五、全量验收矩阵：逐项产生新证据后才能打勾

A. 来源一致：mck、全部实际加载的 .so、模型、原图配置与来源指纹；每台机器人运行身份。
B. 时序和 22 关节：2 ms 同源时钟、编码器/IMU、串并联、q/qd/tau/kp/kd/限幅；过期/异常边界。
C. 模式：阻尼、准备、行走、K1 支持的足球/Custom/其他模式；启动、停机、转换和拒绝条件。
D. 行走：原厂各支持 gait，前后/左右/转向/复合/启停；跟踪误差、足滑、限位与力矩。
E. 保护与恢复：主动前/后/侧倒、外推、姿态不安全；原厂保护/起身及重入行走。
F. 踢传与头臂：原厂动作、视觉输入、动作阶段和实际球接触/位移，不能以请求次数代替成功。
G. 集成：3 官方对 3 原厂完整控制器，正常渲染相机，主客/开球互换、多场和扰动分组。
H. 部署准备：相同请求/状态适配器的 ARM 构建、实际模块选择、完整配置包与离线回读。
I. 真机：固件/服务/DDS ABI、传感器与闭环资格仍待单独授权；仿真通过不替代真机结果。

所有层分别报告“执行完成”“证据覆盖”“动作/性能结论”，不以单一 PASS 混淆。
原厂全模块图加载只满足 A 的部分，冻结输入只能覆盖 B 的边界部分。

九、用户范围澄清：学习 B-Human 的仿真与真机共用方法

用户所述 .run + SDK + RoboCupDemo 部署链成立：原厂 ARM 固件提供运控服务，
比赛程序在 K1 编译后经 SDK/ROS 2 请求该服务。不需要重编译原厂内部运控源码才能开发或部署比赛程序。
“缺少完整原厂 PC 可重编译源码”仅影响直接本机执行完整原厂运控，不能表述成缺少真机开发路径。

应学习的机制：
1. 共享应用/控制逻辑与模型，明确切换传感器、执行器后端；保留版本、单位、坐标系、采样率和状态语义。
2. Real2sim：从设备资料、已有日志和后续经授权的实测校准模型质量/惯量/关节零位/限位、
   执行器 kp/kd/限幅/延迟、相机内参外参、IMU 符号/噪声/滤波；真实日志回放复查闭环输入。
3. Sim2sim：同输入记录、同应用/模型、同随机种子与请求，比较控制器输出和多物理后端轨迹。
   同名 topic 或加载同一权重不足以证明行为等价；物理结果允许误差，但须有预先约定的量化门槛。
4. Sim2real：同一应用构建 ARM 产物，完整回读配置、模型、接口/模式与依赖；
   真机闭环验证与本地仿真结果分别记录。当前只做本地与离线准备。

目标结构（用户再次澄清后的范围）：
同一份选定的比赛程序（自己的或采用上游的感知、决策、裁判处理、配置与模型）
    -> 相同 SDK / ROS 2 请求和状态契约
       +-- 真机：现有官方 SDK / DDS -> 已安装的匹配版本 1.6 运控 -> K1 硬件
       +-- SimRobot：对应仿真接口 -> 原厂控制参考或经过独立验收的仿真运控后端 -> K1 物理模型

B-Human 自己拥有感知、策略、运动控制代码；它不是 RoboCupDemo 的 SimRobot 版本。
其自有控制代码共同编译到 PC 与 ARM，并分别通过 SimulatedRobot3D 或 BoosterProvider 接 IO。
