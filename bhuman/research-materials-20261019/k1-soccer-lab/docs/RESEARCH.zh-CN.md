# K1 足球运控升级：研究证据与实施方案

核验日期：2026-10-19（UTC）。研究对象：Booster K1、B-Human 2026、清华火神反应式足球，以及能沿用真机部署接口的 RoboCup 仿真系统。

## 1. 结论与本次交付的实际进度

建议采用“B-Human 完整比赛系统 + 官方 K1 运动训练基线 + 反应式足球技能迁移 + 独立机器人部署仿真”的路线。先保留现成感知、定位、角色分配、传球/射门/防守和裁判逻辑，再用可测量的实验升级运动技能与球队决策。这既符合现有开放材料，也有利于把训练结果最终做成可回滚的软件版本。

这里的“高级步态”涉及三个不同层次：底层行走与平衡，走踢起身等动作技能，以及队友协作和攻防策略。三层需要共同验证，不能只更换一个行走网络就推定球队能力提升。B-Human 自身已经采用这类分层组织。[S01–S04]

| 项目 | 本次实际状态 | 证据边界 |
|---|---|---|
| 开源基线 | 锁定 B-Human 比赛/训练仓库、子模块、HSL 协议/规则、NUSim 版本 | 审计源码与关键配置；未编译全部比赛程序 |
| 官方 K1 物理回放 | 已运行 16 秒，800 次 50 Hz 推理，无跌倒阈值触发，无数值警告 | 官方预训练策略；单机器人、平地、短时；没有新训练 |
| 六 IP 协议 | 六个独立 127.0.0.x 地址完成 UDP 控制/回报 | 本机回环；没有外部真实裁判机、局域网隔离或 DDS |
| 协议与更新包测试 | 29 项通过，含官方 C 头字节一致性、升级与回滚 | 工具工程测试；不等于机器人运动验收 |
| 可执行 .run | 实现构建、完整性检查、绝对路径安装、版本切换与回退 | artifact_kind=tooling；没有训练完成的新策略，不刷电机固件 |
| 新策略与完整比赛 | 尚未完成 | 需要 GPU、K1 硬件合同、完整传感/SDK 仿真和实际联调 |

原始实验结果与脚本在 `experiments/bhuman_cpu_baseline/`，综合测试记录在 `docs/validation-results.json`。`.run` 是后续版本发布机制的可运行原型，不能作为已训练成功的升级包使用。

## 2. B-Human 2026 到底公开了什么

### 2.1 两个官方仓库必须一起使用

官方于 2026-10-15 发布 Code Release 2026，当前目标为 Booster K1/T1，已移除 NAO。比赛系统与训练框架分属两个仓库；只看比赛仓库会低估其训练材料的完整程度。[S01–S03]

| 用途 | 版本 |
|---|---|
| 比赛程序、感知定位、行为、SimRobot | BHumanCodeRelease，tag coderelease2026，commit 2e3374ba896da8288607f9a1881b876642fe18b8 |
| 行走、踢球、常规起身训练 | MachineLearning，master，commit c3fed817e6e8fd06418bea824b1f1ab0157379d2 |
| CompiledNN 子模块 | 8332c8759f3911e08ded6ac7e088f85620b4c4b5 |
| SimRobot 子模块 | 9deb6ae6b2a553211612affb757490736f96bfb3 |
| pybind11 子模块 | 0bd8896a4010f2d91b2340570c24fa08606ec406 |

版本锁和下载工具包含这些信息。下载工具递归初始化子模块；本次没有把拉取全部依赖等同于完成编译。正式训练/部署还要固定依赖镜像、GPU 驱动、物理资产、归一化、关节映射和电机参数。

### 2.2 已开放训练与仍有缺口的部分

行走与踢球有训练环境、PPO/历史策略实现、机器人资产、训练配置、checkpoint 与 ONNX。常规起身也有训练入口。额外快速起身策略来自另一条 mjlab_playground 管线，当前仓库没有等同完整的训练配方；上游还明确记录它在独立 MuJoCo/实机与比赛仿真之间的行为差异。因此快速起身不应直接放入“已完成仿真一致性”的版本清单。[S03、S05]

官方 K1 行走 checkpoint 续训入口如下，工作目录为 `MachineLearning/IsaacGymRL`：

```bash
python train.py --history --task=K1 \
  --checkpoint=pre-trained/WalkAndKick/K1_walk.pth --headless=1
```

训练依赖是 legacy Isaac Gym Preview 4、Python 3.8、PyTorch 2.0 / CUDA 11.8；与本次 Python 3.12 CPU ONNX 回放是两套环境。先复现官方旧栈，再评估迁移 Isaac Lab；同时改训练框架、物理模型和奖励会难以定位收益与退化来源。[S03]

checkpoint 加载恢复模型并尝试恢复 optimizer，但未恢复迭代号、RNG 和环境状态，所以是续训/微调入口，不是逐比特断点恢复。上游 `convert.py` 硬编码 T1 文件和 `(1,62)` 输入，不能原样用来导出 K1 历史行走网络。应参数化导出，并比较同一批观测在 PyTorch、ONNX 和生产 C++ 中的输出。[S05]

### 2.3 不能破坏的模型合同

| 接口 | 已核实的 K1 walk 合同 |
|---|---|
| 原始 ONNX 输入 | float32，名称 input，形状 [batch_size, 344] |
| 原始 ONNX 输出 | float32，名称 output，形状 [batch_size, 13] |
| 344 维组成 | 10 帧 × 32 维历史 + 24 维当前信息 |
| 13 维输出 | 12 个腿关节角度偏置 + 1 个步频偏置 |
| 策略频率 | 50 Hz；官方训练物理步长 2 ms、decimation 10 |
| 历史内容 | 投影重力、陀螺仪、去默认姿态的关节角、前一动作及占位维 |
| 当前内容 | 速度命令、步态相位、关节速度、前一步频及占位维 |
| 踢球合同 | 59 输入 / 13 输出，无 10 帧历史；使用专门的 walk-start-for-kick checkpoint |

原始 ONNX 是二维张量。WalkingEngine 中的 rank=1 是 CompiledNN 包装隐藏 batch 维后的抽象，不能据此修改模型成一维。关节顺序、角度单位、球坐标系、速度缩放、默认姿态、动作限幅、PD 增益和历史初始化都属于部署合同，形状匹配只是其中一项。[S04–S05]

B-Human 原本就有惯性/编码器噪声、零偏、质量/质心、刚度/阻尼、摩擦、接触参数与外力随机化。新的鲁棒性方法必须与这个已随机化的基线比较；只给观测添加高斯噪声不足以构成可信的升级证据。[S03、S05]

## 3. 火神论文的确切含义与迁移方法

### 3.1 已核验的论文与材料

用户提到的工作是《Learning vision-driven reactive soccer skills for humanoid robots》，发表于 Science Robotics 11(117)，2026-08-19，DOI 10.1126/scirobotics.aed1152。采用 arXiv 2511.03996 的 v2（2026-08-20）交叉核对。平台为 Booster T1，而不是 K1。[S06–S08]

作者 Zenodo 记录 21620490 发布了约 19.7 MB 的 code.zip；已下载并与记录中的 MD5 核对一致。归档含 PPO/AMP 训练、历史编码与辅助重建、T1 YAML/环境、模型 checkpoint、T1 URDF/XML 和重定向动作 CSV。它不只是一段演示视频。[S09]

| 论文结果 | 应如何理解 |
|---|---|
| 距球 1.5 m，约 1.5 s 完成触球 | 是起动至触球的任务完成时间，不是纯感知反应延迟 |
| 视觉 25 Hz，策略 50 Hz | 不代表端到端闭环只需 20 ms |
| 感知延迟均值 116 ms、标准差 18 ms | 说明必须显式处理迟到观测与历史状态 |
| 踢球前 1 s 球位置 RMSE 0.344 m → 0.186 m | 针对论文条件的抗噪改进，不能直接外推 K1 |
| 前场 80–90%、后场 60–70%，各位置 10 次 | 是有限实机测试中的踢球成功率；那组实验未摔倒不等于任意条件都稳定 |
| 论文报告 8 张 V100、16,384 环境、约一天 | 是作者实验配置，不是本项目的 GPU 预算或完成时间承诺 |

这些数值依据最新论文与作者材料；更完整的逐项出处在 `docs/evidence/huoshen_findings.md`。[S06–S09]

### 3.2 火神有团队配合，但不全在公开策略里

最新论文附录 G 的完整比赛架构包含行为树，负责规则、角色和多人协调。学习得到的反应式策略只在主攻手具有空间优势、球较近、前方净空等条件满足时激活，并有超范围/超时退出逻辑。公开单机器人 actor 主要处理自身、球与球门，不含完整队友/对手战术决策输入。[S08–S09]

这支持保留 B-Human 上层系统的路线：普通行走与定位、传球选择、防守站位、裁判状态沿用现成层次；在适当时机调用经过 K1 适配的反应式技能。后续再将上层策略学习化，避免把规则处理与全身运动一起从零探索。

### 3.3 T1 → K1 需要重新训练的部分

公开火神模型有 58 维观测、50 帧历史和 15 维动作。T1 资产中 23 个 joint 标签包含 8 个固定手臂关节，实际控制头部 2、腰部 1、腿部 12。K1 没有相同腰部结构；关节数接近也不表示 checkpoint 可以直接部署。[S09]

建议依次做：将 K1 实际质量、惯量、足底几何和驱动限位纳入模型；把参考动作重新重定向到 K1 并检查支撑足接触；按 K1 重新定义动作、观测和 PD；先复现 B-Human 行走，再训练反应式追球/踢球；最后验证技能切换的相位、历史、目标关节与力矩连续性。

火神值得迁移的核心是“含时延与遮挡的虚拟感知、历史信念表示、辅助状态重建、动作先验和课程训练”。不是把 T1 的腰关节权重删除后直接替换模型。

公开 `play_mujoco.py` 用 qpos 真值构造球/球门观测，再加简化视场与延迟；归档没有完整真实相机检测、定位、比赛行为树、队伍通信、GameController 或真机 SDK runner。因此该播放器不能作为完整视觉比赛或真机部署等价的验收环境。[S09]

## 4. 系统架构：运动、技能、团队分别升级

### 4.1 建议保留的层次

| 层次 | 输入与输出 | 起点与升级方向 |
|---|---|---|
| 传感与状态估计 | 相机/IMU/关节/时间戳 → 自身、球、对手和队友的局部估计 | B-Human 感知定位；加入延迟、置信度、观测年龄与实测漂移处理 |
| 比赛与团队决策 | 局部估计、受限队友通信、GC → 角色、目标位置、传/射/防守意图 | 保留 B-Human 角色与战术；后续受约束的分散策略训练 |
| 动作技能管理 | 高层意图 → 走、急停换向、反应踢球、起身 | 明确激活/退出条件与切换连续性，保持旧技能回归 |
| 低层策略 | 可测状态及历史 → 关节请求、步频 | B-Human 50 Hz K1 actor，针对实测扰动微调 |
| 设备与监督 | SDK、状态门、限位、模式与进程健康 | 真机与仿真走同一接口合同；单一运动控制拥有者 |

表中分层属于工程建议。B-Human 已有去中心化角色选择、主攻手竞争、射门/传球/解围/盘带和站位分配，不需要从零发明球队行为。[S02、S10]

### 4.2 团队策略学习放在高层

第一步用固定 B-Human 球队做基线和对手。随后可以让高层策略输出角色、目标区域、传球对象或技能选择，由成熟低层执行。5–10 Hz 的高层策略是初始设计建议，需要按闭环延迟和战术实验调整；50 Hz 低层合同则来自已核实的 B-Human 基线。

训练可采用集中 critic、分散 actor（CTDE），配合 MAPPO 等可复现基线、不同历史对手组成的自博弈池和角色随机化。critic/teacher 可以用训练真值；部署 actor 必须只看自己的传感估计及规则允许的报文。团队奖励应结合净进球、失球、推进、有效接应、传球价值与规则约束，避免只奖励靠近球导致所有队员争抢。

不要仅按同队训练胜率判定有效。要与固定官方基线、不同风格对手、旧版本和未见过的队形比赛，记录角色切换、重复抢球、传球完成、被截断、防线暴露及通信成本。新策略应在同一硬件时限与规则预算下比较。

## 5. 如何把“大多数情况下稳定”变成实验

### 5.1 先测分布，再随机化

随机化范围首先来自具体 K1 的日志、台架或受控运动数据，而不是越大越好。过强且不真实的扰动会使策略过度保守，牺牲用户要求的快速反应。要保存采样过程、单位、频谱、相关性和状态条件，再区分训练覆盖范围与未见过的组合。

| 扰动类别 | 应覆盖的机制 | 对应指标 |
|---|---|---|
| IMU / 编码器 | 零偏漂移、标定误差、相关噪声、饱和、丢样与时间戳抖动 | 状态估计误差、速度跟踪、姿态恢复、跌倒率 |
| 视觉 | 延迟与抖动、漏检/误检、遮挡、光照、模糊、视场、观测陈旧 | 球状态误差、失球恢复时间、起动至触球/决策延迟 |
| 电机与机体 | PD/摩擦/回差、扭矩与速度限制、质量/质心、温度和电压导致的性能变化 | 饱和比例、跟踪误差、能耗、连续运行退化 |
| 地面与接触 | 草皮/地毯摩擦、磨损、足底形变、球摩擦与恢复系数 | 滑移、急停距离、踢球方向/速度、接触失败 |
| 对抗 | 扰动方向/时机、轻碰撞、急转追球、单足支撑冲击 | 恢复时间、跌倒/起身、碰撞与失球 |
| 计算与通信 | 推理超时、CPU/GPU 争用、DDS/队友丢包、乱序、限额 | p95/p99 延迟、超期率、停机/失联处理、团队退化 |

火神和 Miki 等工作的启示是通过历史推断当前可信状态，并学习在外部感知不可靠时使用本体感觉。工程上应给观测带时间戳与年龄，预测至当前时刻；随意增加低通滤波可能增大相位滞后，需要把抗噪收益与反应延迟一起评估。[S08、S16]

### 5.2 验收矩阵

以下为建议的验收设计，不是已经测得的成绩。正式阈值应由基线、硬件约束和目标赛事共同决定。

| 验收层级 | 必测内容 | 比较与记录方式 |
|---|---|---|
| 模型合同 | 单位/顺序/频率/归一化/动作限幅/导出一致性 | 相同观测的 PyTorch–ONNX–C++ 差异；失败拒绝发布 |
| 运动 | 直走、侧移、后退、急停、反转、组合速度、外力恢复 | 相同命令/随机种子，报告跟踪误差、跌倒/机器人小时、p95/p99 |
| 技能 | 追球、移动球、踢球、起身、技能连续切换 | 全部尝试为分母，失败/超时/进程崩溃均计入 |
| 多机 | 攻防、传球、角色切换、少人、通信丢失、不同对手 | 净进球、失球、胜平负、置信区间、通信预算 |
| 部署 | 安装、重复安装、坏包、升级失败、回退、重启 | 在同一虚拟机器人镜像与真实 SDK 合同上执行 |
| 真机 | 机型/参数/场地变异、整场时长、热与电压状态 | 受控逐级验证，记录实机失败和中断原因 |

训练至少使用多个种子（初始建议 3 个），评估使用独立种子、未见过的扰动组合和对手。保留全部试验与中止，不挑成功视频。对于零跌倒结果仍应给有限样本上界：例如在独立同分布的 300 次试验中零失败，单侧 95% 二项分布失败率上界约为 1%；这仍不覆盖分布之外的机况与碰撞。

本次只有 16 秒正常回放，不能据此给出“大多数情况下稳定”的成功率。其作用是把官方资产、ONNX 推理和物理回放连通，为后续实验提供可复现起点。

## 6. 仿真 RoboCup 如何接近真实部署

### 6.1 需要同时具备的两类仿真

训练环境追求并行吞吐，可以使用特权 critic 和加速时钟。部署比赛仿真则要求每个机器人作为独立程序运行，用本机传感管线和 SDK 消息控制，服从真实 GC 与网络约束。两者共享资产/合同与策略版本，但评估权限和时钟不同。

建议以 B-Human SimRobot 复现现成球队行为和真实渲染场景，同时评估用 MuJoCo 实现 Booster SDK 边界。共享的物理世界负责接触、球和渲染；每个机器人运行独立进程、配置、IP、状态文件及 SDK 桥。禁止使用全局共享队伍真值代替真实队友通信。

完整部署一致性至少包括：同一来源的程序与模型、同一预处理与估计器、同一低层模式/关节映射、同一 IPC/网络接口、同一比赛服务生命周期、同样的安装与回滚流程。若训练机是 x86_64 而 K1 是 ARM，应该从同一源码分别构建目标架构产物；不能声称两个架构原生运行同一个二进制。仿真无法完全再现真实摩擦、硬件故障、温度与计算时序，仍需硬件在环与真机验收。

### 6.2 B-Human SimRobot 与 NUSim 的实际能力

| 方案 | 可复用能力 | 不能据此推定已实现的内容 |
|---|---|---|
| B-Human SimRobot | 已有 K1 多人数场景、比赛程序、行为/感知调试 | 同一进程的多机器人不自动具有独立真实网络身份 |
| PerceptOracle / Fast 场景 | 行为排错、快速回归 | 跳过部分渲染/感知或使用模型真值，不能计入最终视觉部署成绩 |
| NUbots NUSim K1 | MuJoCo、LowState/LowCmd、CUSTOM 低层控制、头部相机共享内存、GC supervisor | 当前多机参数主要生成多机器人，只有主机器人受控，其余以 PD 保持姿态 |
| NUSim 高层 SDK RPC | 接收部分命令/模式切换 | Move/GetUp/VisualKick 等接受但未实现真实行为，不能替代完整 SDK 功能 |

NUSim 是有价值的 SDK 仿真参考，不是开箱即用的六个自主 K1 联赛。其行走模型合同为 79 观测 / 22 动作，与 B-Human 的 344 / 13 不同；默认 host 网络与共享 IPC 也不构成每台机器人隔离。选择它时应保留 SDK 消息思路，重新核验生产预处理和多机隔离。[S11–S13]

### 6.3 一个机器人一个 IP

建议示例拓扑：GC 为 192.168.50.2；蓝队 192.168.50.11/.12/.13；红队 192.168.50.21/.22/.23。地址仅示例，真实比赛必须使用主办方分配的网络设置。

默认 Docker bridge 使用 NAT，外部往往只看到宿主地址；host 网络共享宿主 IP，也不代表六个网络身份。可在支持的 Linux 有线网络上选择 macvlan/ipvlan，或 TAP/桥接的 network namespace。macvlan 的宿主与子接口通信需要另设接口/路由；根权限、云网络和无线网卡支持也各有约束。部署前必须用真实 GC 所在机器验证广播到达和回报源 IP。[S14–S15]

DDS 隔离要额外处理。真实 SDK 可能固定 domain 0 和 topic 名称，仅给机器人不同 ROS 名字并不能防止 LowCmd 串到另一台机器人。应让每个虚拟机器人具有独立网络/桥接端点，并用消息身份、收发计数和错误注入证明确实只控制自己的关节。

当连接真实 GC 时，比赛仿真应以真实墙钟 1× 运行。加速训练时使用独立仿真裁判适配器和仿真时钟，避免真实裁判状态、回报频率和加速物理不一致。

## 7. 当前 HSL GameController 协议

2026 Humanoid Soccer League 已整合原 HL/SPL。应锁定当前 HSL 仓库和赛事规则，而不是沿用旧 HL 或 SPL 的报文尺寸。此次核对固定 GC commit a6cc98bb9f7c0f03912134b333194af3fa880798 的官方 C 头及 Rust serializer。[S17–S19]

| 通道 | 当前格式 | 使用要求 |
|---|---|---|
| GC → 球员 | UDP 3838；RGme；version 20；158 字节 | 正常约 2 Hz；明确处理 stopped、处罚、状态和超时 |
| 球员 → GC | UDP 3939；RGrt；version 4；32 字节 | 每台机器人以自身 IP 单播回报；允许 0.5–2 Hz，工具采用 1 Hz |
| 队内通信 | UDP 10000 + 队号；单包不超过 512 字节 | 使用受限广播，遵守 GC 给出的队伍消息预算 |
| 监控真值 | RGTD；另有监控请求/转发端口 | 只允许评估侧使用，不能输入球员 actor |

回报中的 pose 和球位置为毫米，角度为弧度；浮点和整数按明确小端线格式处理。部分 PLAYING 转换的真实状态会被 GC 暂时隐藏，因此球员程序还需现有哨声/事件逻辑。仅看 state=PLAYING 不足以放行运动，stopped 和处罚要优先处理。[S17]

HSL 规则禁止使用场外计算充当比赛机器人的大脑。仿真可以共享宿主硬件，但每个机器人必须限定独立观测、计算资源和合法通信，才能对现实比赛有意义。规则中的体型/重量级和赛事人数不能按 K1 型号自行猜定，应核对具体机器与赛事分组。[S18–S19]

本项目协议工具对照官方 C 结构编译字节样本，再验证 Python 解码/编码；拒绝旧版本、错误长度、监控真值、非有限/溢出浮点和重复乱序包。`diagnostic_gate` 只输出诊断意图，不是完整规则引擎或物理安全控制器。

## 8. .run 版本发布应做到什么

### 8.1 本次可运行原型

工具包支持 `--verify`、`--install-root /absolute/path` 和 `--rollback --install-root /absolute/path`。每个版本有文件清单、大小与 SHA256；安装先校验再发布版本目录；current/previous 分别使用原子链接替换；已有非项目目录、损坏版本、路径穿越、符号链接和同版本不同内容会被拒绝。

以下是本次生成包的工作区绝对路径用法；下载到其他电脑后应换成实际路径：

```bash
/workspace/scratch/ddfc9e6d5cc3/deliverables/k1-soccer-tooling-0.1.0.run --verify

/workspace/scratch/ddfc9e6d5cc3/deliverables/k1-soccer-tooling-0.1.0.run \
  --install-root /tmp/k1-soccer-tooling-user-demo
```

第一次安装目标必须不存在。`.run` 使用 Linux/POSIX 与 Python 3.10+，只安装研究工具；完整源码 ZIP 另含测试、打包器和物理回放实验。直接 `./filename.run` 与绝对路径执行都依赖可执行权限，下载后可在确认来源的本地文件上使用 `chmod +x`。

### 8.2 正式 K1 版本仍需要补齐

真正的运动版本应包括针对目标架构的应用、ONNX、归一化与参数、明确的机器人/系统镜像/SDK/驱动合同、发布证据和必要许可证。个体标定、机器人身份与网络地址应保存在版本目录外，升级不应覆盖它们。

发布流程应验证可信发布者签名和兼容性；停止旧运动进程并确认控制权交接；安装候选版本；执行静态与非运动健康检查；按经过验证的启动协议激活；健康失败恢复旧版本并记录原因。只能有一个控制器拥有运动输出。

当前 SHA256 校验是完整性检查，不是数字签名。包自身执行的 `--verify` 不能认证一个未知来源的可执行文件；正式发行需要包外可信验证器或等价信任链。当前两个链接分别原子替换，不承诺断电下的跨链接事务恢复，也不自动重启机器人服务。这些是具体待实现项，并不影响本次工具原型的本地演示。

应优先封装 B-Human 现有安装/更新流程并核验 K1 系统镜像，而不是猜测厂商电机固件刷写命令。用户最终需要的日常“一次执行更新运控版本”可以实现，但要以已验收策略和硬件合同为前提。[S20]

## 9. 实施路线与停止条件

| 阶段 | 工作与产物 | 进入下一阶段的条件 |
|---|---|---|
| P0 基线 | 官方固定版本、资产校验、生产预处理对照、SimRobot 对打 | 官方策略和部署行为可复现，异常有日志与定位 |
| P1 鲁棒行走 | 从 K1 checkpoint 续训；实测域随机化、急停换向、推扰与延迟消融 | 在独立测试分布上降低失败且不牺牲关键响应/旧能力 |
| P2 反应足球技能 | K1 动作重定向，历史估计、遮挡/时延训练，连续追踢 | 真实视觉链/SDK 仿真通过；相同任务中优于官方基线 |
| P3 球队协作 | 固定行为基线、受限通信、高层 CTDE/自博弈、对手池 | 多场多种子对比改善攻防，同时规则/消息预算合格 |
| P4 部署比赛仿真 | 六独立进程/IP/SDK、单一物理世界、真实 GC、1× 时钟 | 安装、升级、比赛、失联、回退的全过程联调通过 |
| P5 真机发行 | 目标 K1 架构构建、签名、兼容性门禁、受控分级试验 | 真机长时/扰动/技能/比赛验收完成，才标记正式运控版 |

P0 与 P4 的基础设施可并行；P1/P2/P3 的算法收益必须回流到统一比赛评估。不要只看训练奖励。若出现性能提升来自 oracle、更多计算资源、未计入失败或不公平对手，应回到同条件实验再比较。

当前没有可用训练 GPU、K1 真机/SDK 环境或真实局域网裁判端，所以本次没有启动新策略训练或声称完成 P4/P5。不需要先购买新平台；先提供现有 GPU 型号/显存/数量和 K1 版本，再选择复现栈、并行环境数与实验预算。
