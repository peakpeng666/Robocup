2.2 已开放训练与仍有缺口的部分

行走与踢球有训练环境、PPO/历史策略实现、机器人资产、训练配置、checkpoint 与 ONNX。常规起身也有训练
入口。额外快速起身策略来自另一条 mjlab_playground 管线，当前仓库没有等同完整的训练配方；上游还明确
记录它在独立 MuJoCo/实机与比赛仿真之间的行为差异。因此快速起身不应直接放入“已完成仿真一致性”的版
本清单。[S03、S05]

官方 K1 行走 checkpoint 续训入口如下，工作目录为 MachineLearning/IsaacGymRL：

 python train.py --history --task=K1 \

   --checkpoint=pre-trained/WalkAndKick/K1_walk.pth --headless=1


训练依赖是 legacy Isaac Gym Preview 4、Python 3.8、PyTorch 2.0 / CUDA 11.8；与本次 Python 3.12 CPU
ONNX 回放是两套环境。先复现官方旧栈，再评估迁移 Isaac Lab；同时改训练框架、物理模型和奖励会难以定位
收益与退化来源。[S03]

checkpoint 加载恢复模型并尝试恢复 optimizer，但未恢复迭代号、RNG 和环境状态，所以是续训/微调入口，不
是逐比特断点恢复。上游 convert.py 硬编码 T1 文件和 (1,62) 输入，不能原样用来导出 K1 历史行走网络。应参数
化导出，并比较同一批观测在 PyTorch、ONNX 和生产 C++ 中的输出。[S05]

3.2 火神有团队配合，但不全在公开策略里

最新论文附录 G 的完整比赛架构包含行为树，负责规则、角色和多人协调。学习得到的反应式策略只在主攻手具
有空间优势、球较近、前方净空等条件满足时激活，并有超范围/超时退出逻辑。公开单机器人 actor 主要处理自
身、球与球门，不含完整队友/对手战术决策输入。[S08–S09]

这支持保留 B-Human 上层系统的路线：普通行走与定位、传球选择、防守站位、裁判状态沿用现成层次；在适当
时机调用经过 K1 适配的反应式技能。后续再将上层策略学习化，避免把规则处理与全身运动一起从零探索。

3.3 T1 → K1 需要重新训练的部分

公开火神模型有 58 维观测、50 帧历史和 15 维动作。T1 资产中 23 个 joint 标签包含 8 个固定手臂关节，实际控
制头部 2、腰部 1、腿部 12。K1 没有相同腰部结构；关节数接近也不表示 checkpoint 可以直接部署。[S09]

建议依次做：将 K1 实际质量、惯量、足底几何和驱动限位纳入模型；把参考动作重新重定向到 K1 并检查支撑足
接触；按 K1 重新定义动作、观测和 PD；先复现 B-Human 行走，再训练反应式追球/踢球；最后验证技能切换的
相位、历史、目标关节与力矩连续性。

火神值得迁移的核心是“含时延与遮挡的虚拟感知、历史信念表示、辅助状态重建、动作先验和课程训练”。不
是把 T1 的腰关节权重删除后直接替换模型。

公开 play_mujoco.py 用 qpos 真值构造球/球门观测，再加简化视场与延迟；归档没有完整真实相机检测、定位、
比赛行为树、队伍通信、GameController 或真机 SDK runner。因此该播放器不能作为完整视觉比赛或真机部署
等价的验收环境。[S09]

4.2 团队策略学习放在高层

第一步用固定 B-Human 球队做基线和对手。随后可以让高层策略输出角色、目标区域、传球对象或技能选择，由
成熟低层执行。5–10 Hz 的高层策略是初始设计建议，需要按闭环延迟和战术实验调整；50 Hz 低层合同则来自已
核实的 B-Human 基线。

训练可采用集中 critic、分散 actor（CTDE），配合 MAPPO 等可复现基线、不同历史对手组成的自博弈池和角色
随机化。critic/teacher 可以用训练真值；部署 actor 必须只看自己的传感估计及规则允许的报文。团队奖励应结
合净进球、失球、推进、有效接应、传球价值与规则约束，避免只奖励靠近球导致所有队员争抢。

不要仅按同队训练胜率判定有效。要与固定官方基线、不同风格对手、旧版本和未见过的队形比赛，记录角色切
换、重复抢球、传球完成、被截断、防线暴露及通信成本。新策略应在同一硬件时限与规则预算下比较。


5. 如何把“大多数情况下稳定”变成实验

5.1 先测分布，再随机化

随机化范围首先来自具体 K1 的日志、台架或受控运动数据，而不是越大越好。过强且不真实的扰动会使策略过度
保守，牺牲用户要求的快速反应。要保存采样过程、单位、频谱、相关性和状态条件，再区分训练覆盖范围与未
见过的组合。

6. 仿真 RoboCup 如何接近真实部署

6.1 需要同时具备的两类仿真

训练环境追求并行吞吐，可以使用特权 critic 和加速时钟。部署比赛仿真则要求每个机器人作为独立程序运行，用
本机传感管线和 SDK 消息控制，服从真实 GC 与网络约束。两者共享资产/合同与策略版本，但评估权限和时钟不
同。

建议以 B-Human SimRobot 复现现成球队行为和真实渲染场景，同时评估用 MuJoCo 实现 Booster SDK 边界。
共享的物理世界负责接触、球和渲染；每个机器人运行独立进程、配置、IP、状态文件及 SDK 桥。禁止使用全局
共享队伍真值代替真实队友通信。

完整部署一致性至少包括：同一来源的程序与模型、同一预处理与估计器、同一低层模式/关节映射、同一 IPC/网
络接口、同一比赛服务生命周期、同样的安装与回滚流程。若训练机是 x86_64 而 K1 是 ARM，应该从同一源码分
别构建目标架构产物；不能声称两个架构原生运行同一个二进制。仿真无法完全再现真实摩擦、硬件故障、温度
与计算时序，仍需硬件在环与真机验收。

6.3 一个机器人一个 IP

建议示例拓扑：GC 为 192.168.50.2；蓝队 192.168.50.11/.12/.13；红队 192.168.50.21/.22/.23。地址仅示例，
真实比赛必须使用主办方分配的网络设置。

默认 Docker bridge 使用 NAT，外部往往只看到宿主地址；host 网络共享宿主 IP，也不代表六个网络身份。可在
支持的 Linux 有线网络上选择 macvlan/ipvlan，或 TAP/桥接的 network namespace。macvlan 的宿主与子接口
通信需要另设接口/路由；根权限、云网络和无线网卡支持也各有约束。部署前必须用真实 GC 所在机器验证广播
到达和回报源 IP。[S14–S15]

DDS 隔离要额外处理。真实 SDK 可能固定 domain 0 和 topic 名称，仅给机器人不同 ROS 名字并不能防止
LowCmd 串到另一台机器人。应让每个虚拟机器人具有独立网络/桥接端点，并用消息身份、收发计数和错误注入
证明确实只控制自己的关节。

当连接真实 GC 时，比赛仿真应以真实墙钟 1× 运行。加速训练时使用独立仿真裁判适配器和仿真时钟，避免真实
裁判状态、回报频率和加速物理不一致。

8. .run 版本发布应做到什么

8.1 本次可运行原型

工具包支持 --verify、--install-root /absolute/path 和 --rollback --install-root /absolute/path。每个版本有文
件清单、大小与 SHA256；安装先校验再发布版本目录；current/previous 分别使用原子链接替换；已有非项目目
录、损坏版本、路径穿越、符号链接和同版本不同内容会被拒绝。

以下是本次生成包的工作区绝对路径用法；下载到其他电脑后应换成实际路径：

 /workspace/scratch/ddfc9e6d5cc3/deliverables/k1-soccer-tooling-0.1.0.run --verify



 /workspace/scratch/ddfc9e6d5cc3/deliverables/k1-soccer-tooling-0.1.0.run \

   --install-root /tmp/k1-soccer-tooling-user-demo


第一次安装目标必须不存在。.run 使用 Linux/POSIX 与 Python 3.10+，只安装研究工具；完整源码 ZIP 另含测试、
打包器和物理回放实验。直接 ./filename.run 与绝对路径执行都依赖可执行权限，下载后可在确认来源的本地文
件上使用 chmod +x。

8.2 正式 K1 版本仍需要补齐

真正的运动版本应包括针对目标架构的应用、ONNX、归一化与参数、明确的机器人/系统镜像/SDK/驱动合同、发
布证据和必要许可证。个体标定、机器人身份与网络地址应保存在版本目录外，升级不应覆盖它们。

发布流程应验证可信发布者签名和兼容性；停止旧运动进程并确认控制权交接；安装候选版本；执行静态与非运
动健康检查；按经过验证的启动协议激活；健康失败恢复旧版本并记录原因。只能有一个控制器拥有运动输出。

当前 SHA256 校验是完整性检查，不是数字签名。包自身执行的 --verify 不能认证一个未知来源的可执行文件；正
式发行需要包外可信验证器或等价信任链。当前两个链接分别原子替换，不承诺断电下的跨链接事务恢复，也不
自动重启机器人服务。这些是具体待实现项，并不影响本次工具原型的本地演示。

A4. 与本项目最直接的新对照：Noisy Striker
Xu 等 ICRA 2026 的官方代码确实公开，而非只找到预印本。它采用四阶段 teacher–student：远距离追球、定向
踢球、带噪声/延迟/遮挡的 DAgger 蒸馏、N-P3O 约束强化学习进一步适配；另有腿惯性里程计训练。这条线与火
神共同回答了“训练真值到部署不完美感知”的问题，是反应技能阶段值得并行复现的基线。[C02]

工程上应对比：原始 B-Human kick；火神式历史重建+动作先验；Noisy Striker 式 teacher–student+适配。统
一 K1 资产、球初始条件、真实感知噪声、控制频率与失败分母，才能判断收益来自算法还是实验条件。现有公开
T1 代码并不能直接证明某个方法在 K1 上更强。
